Case Study · MonRiverGames

Derby

A controller-first platformer racer with rail grinding and wall riding, built in Unreal Engine by the nonprofit studio MonRiverGames. My goal was to give Derby a solid foundation: movement and camera systems that both look and feel good, and a codebase several people can work in without stepping on each other.

Role
Lead Programmer
Engine
Unreal Engine
Language

Controller-only

Systems I built

Vehicle style movement controller

The original movement felt like a standard third-person controller with a bit of drift, not like driving. Because this is a racer, I wanted the movement itself to be what made Derby distinctive.

Problem
Movement followed the mouse and the character turned to face whichever way it was moving. Braking or reversing slid Derby diagonally across the screen instead of backing up.
Approach
I removed strafing so that W accelerates and S brakes or reverses. I turned off orient-to-movement and drove the movement from Get Actor Forward Vector instead of the control rotation, so Derby has a heading of her own. Steering feeds the X-axis input into the yaw (Z) of AddActorLocalRotation.
Result
Derby now drives like a vehicle. Steering is something the player has to master, which adds difficulty that fits the game's theme.

Movement prototypes

When I was asked to explore other movement styles, I pitched three: a push style that moves in bursts on repeated presses, a roller-skate variant built around ramps and momentum, and an omnidirectional platformer variant. I built the push prototype by setting the input action to fire once per press and driving Launch Character with a force multiplier. Splitting steering into its own IA_Rotate action stopped players from having to mash to turn. A teammate tracked down the final input bug that blocked that setup.

In internal playtests, the team chose the original driving model because it fit Derby's theme best. The prototypes did their job: they settled the question with something people could play instead of an argument.

Chase camera

During a playtest, a teammate pointed out that the camera should lock behind Derby while she's moving. I'd never noticed, because as the developer I already knew how everything worked. The camera had been deciding where the player went, and I wanted the player's heading to decide where the camera went.

Research first
Unreal has so many camera features built in that I read through the engine's camera system before writing any logic.
Debugging
Turning off Use Pawn Control Rotation got the camera to follow Derby's rotation, but it stopped aiming at her. I traced the Blueprint for anything else setting rotation and found redundant per-tick Orient Rotation to Movement toggling left over from my movement rewrite, which I removed. Restructuring the rig fixed the aim. Clipping through walls was fixed with Do Collision Test, the probe size, the Camera probe channel, and a missing parent socket on the camera, which was the step everything else depended on.
Result
A working chase camera configured entirely through component settings, with no custom Blueprint code. Camera lag, distance, and height are next, to be agreed with the team.

Rail system refactor

Movement, wall riding, and rail splines all lived in one Third Person Character Blueprint. It was so large it wouldn't fit on screen fully zoomed out, and with several people editing it, merge conflicts were constant.

Option A
A Blueprint Function Library. I ruled it out because function libraries can't hold variables, and the rail and wall-ride logic depends on state.
Option B ✓
A Blueprint component (BPC_Rail) attached to the character. I audited which variables the rail logic actually used, recreated them in the component, moved the nodes over, re-pointed every reference that still targeted the character, and cast to the owning character on BeginPlay.
Result
Rail logic now lives in its own component, so it can be changed without touching the character Blueprint. This is the pattern for moving wall riding out next.
Open issue
The split made an existing bug reproduce more reliably: after jumping off a rail, Derby can render floating above the ground while her logical position is correct. It's easier to track down now that it reproduces consistently.

Bug fixes & input

Rail exits
Rails that ended at odd angles left Derby stuck at a skewed rotation on every axis. I wrote a function, called just before each Launch Character, that resets her upright and keeps only her heading. This was a top-priority fix.
Controller
Wall riding had never been mapped to the gamepad, which blocked playtesting on the input we'd chosen. I mapped it, and Derby became controller-only.
Collectables
The coin collectable still ran on outdated BP_Cart logic. I fixed it so the game has a working collectable.
Cleanup
I removed leftover experimental nodes from the movement input graph so the next person can read it.

Air-spin & trick groundwork (in progress)

Tricks give players a reason to explore Derby's open, nonlinear spaces. As a first step, a Select node driven by IsFalling swaps in a faster rotation rate while Derby is airborne. Next is detecting a full spin: while she's falling, compare this tick's yaw with last tick's, add up the absolute change, and fire a trick event once the total reaches 360°.

Level & technical art

Demo map rework for Bit Bridge

Playtest feedback said the demo was outdated, both in how it played and how it looked. Before Bit Bridge, I rebuilt the opening around the team's plan for a subway hub. I replaced every control sign with Xbox prompts, enclosed the starting area, and lit it with artificial light. I dressed it with subway props, enlarged the starting platform, moved a sign that blocked the first wall ride, extended the return spline so it launches players toward that wall ride, and removed the moving platforms. I'm now rebuilding the tutorial level from scratch.

Material fixes

Brick
Fixed aliasing and z-fighting artifacts that had been present for most of the project. The cause was the material's normal map.
Tile walls
Fixed textures stretching instead of tiling by converting texture samples into texture objects and routing them through world-aligned texture and normal nodes.

Playtesting

I've demoed Derby at public events and folded what I learned straight back into the task list:

  • Retro Reload (Sept 19): showed that the controller build had no wall riding, and that players struggled with a long wall-ride section. That became the controller-input fix and the camera work.
  • October playtest: feedback from other developers made it clear the demo was outdated, which led to the map rework.
  • Bit Bridge: the consistent note was that Derby lacked game feel, especially a prompt showing when a wall ride is possible and how long it can last.

That feedback shaped the game-feel roadmap I proposed:

  • FOV widening and wind particles as Derby approaches top speed
  • Camera shake on big landings
  • A longer ramp up to top speed, so acceleration feels more like a vehicle
  • Auto-rotating and attaching to wall-rideable surfaces, plus wall-ride prompts and a duration indicator

What I learned

  • Read the engine before writing code. The camera ended up needing no custom logic at all, only the right settings.
  • Build modular systems from the start. One large Blueprint shared by a team becomes a merge-conflict problem. Components keep each system's logic separate.
  • Fresh eyes catch what you can't. The camera problem was obvious to a playtester and invisible to me.
  • Keep your branch synced with main. I once had to rebuild a class period's work. It went fast because I understood what I'd built, and now I fetch before I start.
  • Coming from Unity to Unreal: problems that are one line in C#, like swapping a value on a condition, mean finding the right node in Blueprints. I've built up that knowledge across the project.
